# homelight

Telegram-бот, який перевіряє наявність електроенергії в будинку на Полтавській 64
через реле Shelly (Shelly Cloud API) і сповіщає підписників, коли світло зникає
або з'являється.

## Як це працює

- Кожні 90 с бот запитує стан пристрою в Shelly Cloud (`/device/all_status`).
- **Світла немає**, якщо напруга нижча за 100 В. Зміна за напругою **підтверджується
  повторною перевіркою** через 20 с.
- **Стан невідомий**, якщо не вдалося отримати дані (немає інтернету на сервері бота,
  ліміт запитів, збій Shelly Cloud). Такі перевірки ігноруються й не дають хибних сповіщень.
- **Пристрій офлайн** означає, що пропало світло або інтернет у будинку: у моменті це не
  розрізнити. Бот чекає 3 хв (короткі збої інтернету, як-от перезавантаження роутера,
  ігноруються) і повідомляє «🔴 СВІТЛО ПРОПАЛО!». Коли пристрій повертається, бот дивиться
  на його uptime:
  - пристрій перезавантажувався → світло справді зникало: «🟢 СВІТЛО ПОВЕРНУЛОСЬ!» із часом
    увімкнення за даними пристрою (навіть якщо інтернет з'явився пізніше);
  - не перезавантажувався → живлення не зникало: «ℹ️ Світло не зникало — у будинку
    пропадав інтернет».

  Якщо Shelly Cloud не передає uptime (про це буде попередження в логах під час старту),
  повернення пристрою завжди вважається поверненням світла.
- **Перевірка домашнього роутера** (якщо задано `ROUTER_HOST`). Роутер живиться від ДБЖ,
  тож працює й без світла. Коли Shelly офлайн, бот пробує з'єднатися з домашньою (білою)
  IP-адресою:
  - роутер відповідає → інтернет у будинку є, отже **світла в місті немає точно**:
    «🔴 СВІТЛО ПРОПАЛО!» вже за ~20 с, без 3-хвилинного очікування;
  - роутер не відповідає → **збій провайдера**: стан невідомий, підписникам нічого
    не надсилається.

  Деталі див. у розділі «Перевірка роутера».
- **Службові сповіщення лише власнику** (якщо задано `ADMIN_CHAT_ID`). Підписники цих
  повідомлень не отримують.
  - **Інтернет удома.** Якщо задано `ROUTER_HOST`, роутер перевіряється на кожній ітерації,
    незалежно від Shelly. Якщо він мовчить понад 3 хв, приходить «🔴 Вдома немає
    інтернету…», а коли роутер знову відповідає — «🟢 Інтернет удома відновився…».
    Поки триває очікування, перевірки йдуть кожні 20 с. Роутеру, який жодного разу
    не відповів від запуску, бот не довіряє й не повідомляє про нього.
    Ці повідомлення отримує власник і спеціальні користувачі, яких власник додає командою
    `/special` (див. нижче) або змінною `INTERNET_ALERT_CHAT_IDS`.
  - **Дані датчика.** Якщо дані з Shelly Cloud недоступні понад 3 хв (наприклад, через
    недійсний ключ), власник отримує «🟠 Немає даних від датчика світла…» (подробиці — у логах),
    а потім — повідомлення, коли вони знову надходять.

  У текстах повідомлень немає назв пристроїв і сервісів — лише «датчик світла» й «роутер».
- Підтверджений стан і час його початку зберігаються в PostgreSQL (таблиця
  `light_state`), тому перезапуск бота не дає повторних сповіщень і не обнуляє
  тривалість відключення.
- Кнопка «🔌 Перевірити наявність електроенергії» показує поточні дані (з кешем на
  30 с) і нічого не змінює в стані сповіщень.
- Користувачі, які заблокували бота, автоматично відписуються.

## Змінні середовища

| Змінна | Обов'язкова | Опис |
|---|---|---|
| `BOT_TOKEN` | так | токен Telegram-бота |
| `SHELLY_AUTH_KEY` | так | ключ авторизації Shelly Cloud |
| `DATABASE_URL` | так | URL PostgreSQL |
| `SHELLY_BASE_URL` | ні | сервер Shelly Cloud (за замовчуванням `https://shelly-237-eu.shelly.cloud`) |
| `TARGET_MAC` | ні | MAC модуля на лінії міста (за замовчуванням `48f6eeb6ec00`; порожнє значення — перший пристрій) |
| `PLUG_MAC` | ні | MAC розетки в квартирі після перемикача резерву — для повідомлень власнику про резерв (див. «Резерв і бойлер»); порожньо — вимкнено |
| `TIMEZONE` | ні | таймзона для відображення часу (за замовчуванням `Europe/Kyiv`) |
| `DB_SSLMODE` | ні | `sslmode` для PostgreSQL (за замовчуванням `require`; для локальної бази — `disable`) |
| `ROUTER_HOST` | ні | біла IP-адреса (або домен) домашнього роутера на ДБЖ; порожньо — перевірка вимкнена |
| `ROUTER_PORT` | ні | порт роутера для перевірки (за замовчуванням `80`) |
| `ADMIN_CHAT_ID` | ні | Telegram ID власника для службових сповіщень; порожньо — вимкнено |
| `INTERNET_ALERT_CHAT_IDS` | ні | додаткові Telegram ID через кому, які отримують лише повідомлення про інтернет удома (простіше додавати спеціальних користувачів командою `/special`) |

Свій Telegram ID можна дізнатися з бази (ви там є, якщо натискали /start):

```bash
heroku pg:psql -a <app>
```


## Перевірка роутера

Бот з'єднується з `ROUTER_HOST:ROUTER_PORT` і нічого туди не надсилає. Можливі три результати:
- **з'єднання встановлено** (порт відкритий) — роутер точно на зв'язку. Це найнадійніший режим:
  щойно бот хоч раз побачив відкритий порт, далі він вважає інтернет наявним лише за встановленого
  з'єднання. Відкрити порт можна, увімкнувши віддалене керування роутером (у TP-Link зазвичай
  «Додатково → Системні інструменти → Адміністрування → Віддалене керування», назви залежать
  від моделі) на нестандартному
  порту (наприклад, 8443). Обов'язково з надійним паролем адміністратора й оновленою прошивкою;
- **відмова** (порт закритий) — найімовірніше, відповів роутер. Працює без налаштувань, але відмову
  зрідка може надіслати й обладнання провайдера;
- **відповіді немає** — інтернету в будинку немає.

Під час старту бот один раз перевіряє роутер і пише результат у лог (IP-адреса туди не потрапляє),
наприклад: «Роутер (порт 8443) відкритий — перевірка інтернету в будинку працює в найнадійнішому режимі».

Якщо в провайдера окремий оптичний термінал (ONT), він теж має живитися від ДБЖ.

**Запобіжник.** Мовчанню роутера бот довіряє лише після того, як роутер хоч раз відповів від запуску бота.
Якщо роутер не відповідає взагалі (неправильна адреса чи порт, провайдер блокує вхідні з'єднання), бот
працює так, ніби `ROUTER_HOST` не задано, і сповіщення про відключення не губляться.

### Тестовий режим: /testmode (лише для власника)

- `/testmode on` — сповіщення про світло отримує лише власник (з позначкою «🧪»), підписники нічого не отримують;
- `/testmode off` — сповіщення знову отримують усі підписники;
- `/testmode` — показати, чи ввімкнено.

Режим зберігається в базі (таблиця `bot_settings`), тож переживає перезапуски бота. Стан світла при цьому
відстежується як завжди, тож після вимкнення режиму підписники не отримають старих сповіщень.

### Спеціальні користувачі: /special (лише для власника)

Спеціальні користувачі отримують повідомлення про зникнення й відновлення інтернету вдома. Інших
службових повідомлень, сповіщень тестового режиму й команд у них немає. Стара назва команди `/admins`
теж працює.

Повідомлення про інтернет отримують лише ті спеціальні користувачі (і власник теж), хто **підписаний**
на сповіщення про світло. Непідписані позначені в `/special` значком 🔕; щойно людина підпишеться,
повідомлення почнуть надходити. Якщо підписку перевірити не вдалося (збій БД), повідомлення надсилається
всім отримувачам.

1. Людина натискає `/start` у боті.
2. Власник надсилає `/special` → «➕ Додати» → натискає на її ім'я (поруч — @username, якщо він відомий,
   і повний Telegram ID, щоб розрізнити однакові імена). Ім'я та @username бот запам'ятовує при кожній
   взаємодії людини з ботом (у базу пише лише тоді, коли вони змінилися). Нові користувачі — вгорі,
   список гортається кнопками «Далі ➡️» і «⬅️ Попередні» (по 8 на сторінці). Людині приходить
   «👋 Вас додано до спеціальних користувачів…».
3. Видалити — кнопкою «❌» біля імені в `/special`.

Список зберігається в базі (`bot_settings`) і діє одразу, без перезапуску бота. Задані змінною
`INTERNET_ALERT_CHAT_IDS` теж показуються в `/special` з позначкою «задано в Heroku», але видалити їх
можна лише в Heroku.

### Команда /router (лише для власника)

Якщо задано `ADMIN_CHAT_ID`, власник може надіслати боту:
- `/router` — перевірити роутер з налаштувань (`ROUTER_HOST`, `ROUTER_PORT`): чи є інтернет удома,
  а якщо роутер на зв'язку — ще й якість зв'язку: затримка (середня, мінімальна, максимальна) і втрати
  з 5 спроб. Справжню швидкість (Мбіт/с) бот не вимірює: для цього потрібен пристрій удома. Затримку
  варто порівнювати з тим, що зазвичай, бо сервер бота може бути далеко;
- `/router 8443` — разово перевірити інший порт;
- `/router адреса порт` — разово перевірити довільну адресу й порт (працює й без `ROUTER_HOST`).

Разові перевірки не змінюють налаштувань бота: так можна підібрати порт, на який роутер відповідає, і вже
потім задати його в Heroku. Команда нікому нічого не розсилає. Для інших користувачів її немає (бот просто
покаже меню).

Щоб переконатися, що на перевірку відповідає саме ваш роутер, а не обладнання провайдера:
1. `/router` → має бути «відповідає»;
2. вийміть кабель інтернету з роутера і з мобільного інтернету надішліть `/router` → має бути «не відповідає»;
3. вставте кабель назад → `/router` знову «відповідає».

Якщо на кроці 2 бот каже «відповідає», за адресою з `ROUTER_HOST` відповідає не ваш роутер — видаліть цю змінну.

## Резерв і бойлер

Модуль на лінії міста (`TARGET_MAC`) стоїть у щитку **до** ручного перемикача «місто — резерв» і показує,
чи є світло від міста. Розетка (`PLUG_MAC`) стоїть у квартирі **після** перемикача: живлення в ній є і від
міста, і від резерву. Кожне перемикання (через положення 0) знеструмлює розетку, і вона перезавантажується,
тож за моментом її увімкнення видно, від чого вона живиться:

| Ситуація | Модуль на лінії міста | Розетка |
|---|---|---|
| Місто | на зв'язку | увімкнулася не раніше, ніж повернулося місто |
| Резерв | не на зв'язку | під напругою, увімкнулася під час відключення |
| Місто повернулося, ви ще на резерві | щойно увімкнувся | увімкнулася раніше за модуль |

### Повідомлення про резерв (лише власнику)

Якщо задано `PLUG_MAC` і `ADMIN_CHAT_ID`, власник отримує:
- «🔋 Ви перейшли на резерв» — коли й з якого часу немає світла від міста, і чи вимкнений бойлер;
- «🟢 Світло від міста повернулося, а ви ще на резерві — можна перемикатися»;
- «✅ Ви перейшли з резерву на світло від міста» — коли резерв увімкнули, коли вимкнули й скільки він працював;
- «🪫 Резерв вимкнено» — розетка без живлення понад 3 хв (якщо інтернету вдома немає, бот чекає);
- «ℹ️ Резерв не вимикався — пропадав зв'язок» — якщо розетка повернулася без перезавантаження;
- «⚠️ Бойлер увімкнувся, хоча ви на резерві» — запобіжник на випадок, якщо скрипт бойлера не працює.

Поки триває резерв, у відповіді на «Перевірити» власник бачить «🔋 Ви на резерві з …». Стан резерву
зберігається в базі (`bot_settings`), тож перезапуск бота не дає повторних повідомлень. Поки світло від
міста є, резерв ніколи не починається — так перезапуск бота не дасть хибних повідомлень.

Обидва пристрої мають бути в одному акаунті (одна відповідь хмари містить обидва, зайвих запитів немає).

### Скрипт бойлера (`shelly/boiler.js`)

Бойлер вмикається лише від міського живлення. Скрипт працює на самій розетці — без інтернету й без бота:
1. Після кожної появи живлення розетка вимкнена (скрипт сам ставить «Power on default: Off»).
2. Скрипт питає модуль на лінії міста. Не відповідає — міста немає (резерв), бойлер вимкнений.
3. Модуль увімкнувся раніше за розетку (чи разом із нею) — розетка від міста, бойлер вмикається.
   Далі ним можна керувати вручну як завжди.
4. Модуль увімкнувся пізніше за розетку — місто повернулося, а розетка ще на резерві: бойлер вимкнений
   до перемикання на місто.

Поки джерело невідоме або це резерв, бойлер **не вмикається навіть вручну** — скрипт одразу вимикає його назад.

Встановлення:
1. Відкрийте в браузері веб-сторінку розетки (`http://<IP розетки>`, телефон у домашньому Wi-Fi).
2. **Scripts → Create script**, назва `boiler`, вставте вміст `shelly/boiler.js` → **Save** → **Start**.
3. Увімкніть **Run on startup** (інакше після перезавантаження скрипт не запуститься).
4. На початку скрипта — IP модуля (`192.168.31.215`). Закріпіть цю адресу в роутері (резервування DHCP),
   а веб-сторінка модуля має бути без пароля.
5. Перевірка: вийміть розетку й увімкніть знову, поки місто є, — за 10–20 с бойлер увімкнеться;
   рішення видно в консолі скрипта.

Якщо модуль на лінії міста зламається, бойлер не ввімкнеться й від міста: зупиніть скрипт (**Stop**),
і розетка знову керується вручну. Перевірте, що потужність бойлера не перевищує допустиму для розетки.

## Запуск

```bash
pip install -r requirements.txt
python app.py
```

Таблиці в базі створюються автоматично під час старту. Для Heroku-подібних платформ
є `Procfile` (`worker: python app.py`).

## Тести

```bash
python -m unittest discover -s tests -t .
```

Тести SQL (`tests/test_db.py`) запускаються лише з окремою тестовою базою (вони видаляють
таблиці, тому її назва повинна містити `test`):

```bash
TEST_DATABASE_URL=postgresql://user@localhost/homelight_test DB_SSLMODE=disable \
    python -m unittest tests.test_db
```

## Структура

- `app.py` — запуск, обробники команд і кнопок.
- `broadcaster.py` — фонова перевірка й розсилка сповіщень.
- `keyboard.py` — клавіатура з кнопками.
- `light_checker.py` — запити до Shelly Cloud, логіка підтвердження стану, тексти повідомлень.
- `reserve.py` — визначення роботи на резерві й тексти повідомлень власнику.
- `shelly/boiler.js` — скрипт для розетки бойлера (вмикати лише від міста).
- `db.py` — робота з PostgreSQL.
- `config.py` — налаштування зі змінних середовища.
