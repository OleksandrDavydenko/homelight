# homelight

Telegram-бот, який перевіряє наявність електроенергії в будинку на Полтавській 64
через реле Shelly (Shelly Cloud API) і сповіщає підписників, коли світло зникає
або з'являється.

## Як це працює

- Кожні 90 с бот запитує стан пристрою в Shelly Cloud (`/device/all_status`).
- **Світла немає**, якщо напруга нижча за 100 В. Зміна за напругою **підтверджується
  повторною перевіркою** через 20 с.
- **Стан невідомий**, якщо не вдалося отримати дані (немає інтернету на сервері бота,
  ліміт запитів, збій Shelly Cloud). Такі перевірки ігноруються й не дають хибних сповіщень.
- **Пристрій офлайн** означає, що пропало світло або інтернет у будинку: у моменті це не
  розрізнити. Бот чекає 3 хв (короткі збої інтернету, як-от перезавантаження роутера,
  ігноруються) і повідомляє «🔴 СВІТЛО ПРОПАЛО!». Коли пристрій повертається, бот дивиться
  на його uptime:
  - пристрій перезавантажувався → світло справді зникало: «🟢 СВІТЛО ПОВЕРНУЛОСЬ!» із часом
    увімкнення за даними пристрою (навіть якщо інтернет з'явився пізніше);
  - не перезавантажувався → живлення не зникало: «ℹ️ Світло не зникало — у будинку
    пропадав інтернет».

  Якщо Shelly Cloud не передає uptime (про це буде попередження в логах під час старту),
  повернення пристрою завжди вважається поверненням світла.
- **Перевірка домашнього роутера** (якщо задано `ROUTER_HOST`). Роутер живиться від ДБЖ,
  тож працює й без світла. Коли Shelly офлайн, бот пробує з'єднатися з домашньою (білою)
  IP-адресою:
  - роутер відповідає → інтернет у будинку є, отже **світла в місті немає точно**:
    «🔴 СВІТЛО ПРОПАЛО!» вже за ~20 с, без 3-хвилинного очікування;
  - роутер не відповідає → **збій провайдера**: стан невідомий, підписникам нічого
    не надсилається.

  Деталі див. у розділі «Перевірка роутера».
- **Службові сповіщення лише власнику** (якщо задано `ADMIN_CHAT_ID`). Підписники цих
  повідомлень не отримують.
  - **Інтернет удома.** Якщо задано `ROUTER_HOST`, роутер перевіряється на кожній ітерації,
    незалежно від Shelly. Якщо він мовчить понад 3 хв, власник отримує «⚠️ Вдома немає
    інтернету…», а коли роутер знову відповідає — «✅ Інтернет удома відновився (не було …)».
    Поки триває очікування, перевірки йдуть кожні 20 с. Роутеру, який жодного разу
    не відповів від запуску, бот не довіряє й не повідомляє про нього.
  - **Shelly Cloud.** Якщо дані з Shelly Cloud недоступні понад 3 хв (наприклад, через
    недійсний ключ), власник отримує «⚠️ Не вдається отримати дані з Shelly…», а потім —
    повідомлення, коли вони знову надходять.
- Підтверджений стан і час його початку зберігаються в PostgreSQL (таблиця
  `light_state`), тому перезапуск бота не дає повторних сповіщень і не обнуляє
  тривалість відключення.
- Кнопка «🔌 Перевірити наявність електроенергії» показує поточні дані (з кешем на
  30 с) і нічого не змінює в стані сповіщень.
- Користувачі, які заблокували бота, автоматично відписуються.

## Змінні середовища

| Змінна | Обов'язкова | Опис |
|---|---|---|
| `BOT_TOKEN` | так | токен Telegram-бота |
| `SHELLY_AUTH_KEY` | так | ключ авторизації Shelly Cloud |
| `DATABASE_URL` | так | URL PostgreSQL |
| `SHELLY_BASE_URL` | ні | сервер Shelly Cloud (за замовчуванням `https://shelly-237-eu.shelly.cloud`) |
| `TARGET_MAC` | ні | MAC пристрою (за замовчуванням `48f6eeb6ec00`; порожнє значення — перший пристрій) |
| `TIMEZONE` | ні | таймзона для відображення часу (за замовчуванням `Europe/Kyiv`) |
| `DB_SSLMODE` | ні | `sslmode` для PostgreSQL (за замовчуванням `require`; для локальної бази — `disable`) |
| `ROUTER_HOST` | ні | біла IP-адреса (або домен) домашнього роутера на ДБЖ; порожньо — перевірка вимкнена |
| `ROUTER_PORT` | ні | порт роутера для перевірки (за замовчуванням `80`) |
| `ADMIN_CHAT_ID` | ні | Telegram ID власника для службових сповіщень; порожньо — вимкнено |

Свій Telegram ID можна дізнатися з бази (ви там є, якщо натискали /start):

```bash
heroku pg:psql -a <app>
```

```sql
SELECT telegram_id, first_name FROM userslightbot;
```

## Перевірка роутера

Бот з'єднується з `ROUTER_HOST:ROUTER_PORT` і нічого туди не надсилає. Можливі три результати:
- **з'єднання встановлено** (порт відкритий) — роутер точно на зв'язку. Це найнадійніший режим:
  щойно бот хоч раз побачив відкритий порт, далі він вважає інтернет наявним лише за встановленого
  з'єднання. Відкрити порт можна, увімкнувши віддалене керування роутером (у TP-Link зазвичай
  «Додатково → Системні інструменти → Адміністрування → Віддалене керування», назви залежать
  від моделі) на нестандартному
  порту (наприклад, 8443). Обов'язково з надійним паролем адміністратора й оновленою прошивкою;
- **відмова** (порт закритий) — найімовірніше, відповів роутер. Працює без налаштувань, але відмову
  зрідка може надіслати й обладнання провайдера;
- **відповіді немає** — інтернету в будинку немає.

Під час старту бот один раз перевіряє роутер і пише результат у лог (IP-адреса туди не потрапляє),
наприклад: «Роутер (порт 8443) відкритий — перевірка інтернету в будинку працює в найнадійнішому режимі».

Якщо в провайдера окремий оптичний термінал (ONT), він теж має живитися від ДБЖ.

**Запобіжник.** Мовчанню роутера бот довіряє лише після того, як роутер хоч раз відповів від запуску бота.
Якщо роутер не відповідає взагалі (неправильна адреса чи порт, провайдер блокує вхідні з'єднання), бот
працює так, ніби `ROUTER_HOST` не задано, і сповіщення про відключення не губляться.

### Тестовий режим: /testmode (лише для власника)

- `/testmode on` — сповіщення про світло отримує лише власник (з позначкою «🧪»), підписники нічого не отримують;
- `/testmode off` — сповіщення знову отримують усі підписники;
- `/testmode` — показати, чи ввімкнено.

Режим зберігається в базі (таблиця `bot_settings`), тож переживає перезапуски бота. Стан світла при цьому
відстежується як завжди, тож після вимкнення режиму підписники не отримають старих сповіщень.

### Команда /router (лише для власника)

Якщо задано `ADMIN_CHAT_ID`, власник може надіслати боту:
- `/router` — перевірити роутер з налаштувань (`ROUTER_HOST`, `ROUTER_PORT`): результат (відкритий порт,
  відмова чи немає відповіді) і висновок, чи є інтернет у будинку;
- `/router 8443` — разово перевірити інший порт;
- `/router 195.38.8.114 8443` — разово перевірити довільну адресу й порт (працює й без `ROUTER_HOST`).

Разові перевірки не змінюють налаштувань бота: так можна підібрати порт, на який роутер відповідає, і вже
потім задати його в Heroku. Команда нікому нічого не розсилає. Для інших користувачів її немає (бот просто
покаже меню).

Щоб переконатися, що на перевірку відповідає саме ваш роутер, а не обладнання провайдера:
1. `/router` → має бути «відповідає»;
2. вийміть кабель інтернету з роутера і з мобільного інтернету надішліть `/router` → має бути «не відповідає»;
3. вставте кабель назад → `/router` знову «відповідає».

Якщо на кроці 2 бот каже «відповідає», за адресою з `ROUTER_HOST` відповідає не ваш роутер — видаліть цю змінну.

## Запуск

```bash
pip install -r requirements.txt
python app.py
```

Таблиці в базі створюються автоматично під час старту. Для Heroku-подібних платформ
є `Procfile` (`worker: python app.py`).

## Тести

```bash
python -m unittest discover -s tests -t .
```

Тести SQL (`tests/test_db.py`) запускаються лише з окремою тестовою базою (вони видаляють
таблиці, тому її назва повинна містити `test`):

```bash
TEST_DATABASE_URL=postgresql://user@localhost/homelight_test DB_SSLMODE=disable \
    python -m unittest tests.test_db
```

## Структура

- `app.py` — запуск, обробники команд і кнопок.
- `broadcaster.py` — фонова перевірка й розсилка сповіщень.
- `keyboard.py` — клавіатура з кнопками.
- `light_checker.py` — запити до Shelly Cloud, логіка підтвердження стану, тексти повідомлень.
- `db.py` — робота з PostgreSQL.
- `config.py` — налаштування зі змінних середовища.
